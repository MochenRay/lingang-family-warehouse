# 临港家庭数仓项目深度分析报告

> 生成时间：2026-04-14
> 分析目的：为后续细化、重构和迭代提供统一的项目认知基线

## 1. 执行摘要

这个项目当前最准确的定位，不是“可直接上线的家庭数仓系统”，而是一个已经做出较高视觉完成度的 **前端高保真业务原型**。它有完整的桌面端与移动端界面、较成熟的深色设计系统、较多的业务场景页面，以及一套基于 `localStorage + seed` 的本地模拟数据层。

它的优点很明确：

- 设计系统基础已经成型，视觉语言相对统一。
- 页面覆盖面足够大，已经能支撑产品讨论、方案演示和流程推演。
- 核心数据对象已经初步沉淀出来：人口、房屋、网格、走访、公告、纠纷、标签。
- Web 与移动端已经共享部分领域数据，说明后续做真实业务闭环有基础。

它的瓶颈也非常明确：

- 路由、数据层、状态管理、类型校验、测试体系都还停留在原型阶段。
- 多个核心页面是超大单文件，UI、状态、规则、数据拼在一起，后续改动成本会迅速上升。
- 很多“智能体 / AI / 分析”功能仍然是前端模拟，不具备真实业务能力。
- 当前文档中“完成度很高”的表述，和代码里的真实工程成熟度并不等价。

我的判断是：

**这个项目已经具备“继续做”的价值，但不适合继续按“全面铺页面 + 局部打补丁”的方式迭代。**

下一阶段最合理的策略，不是继续平均打磨 60+ 个页面，而是：

1. 先把工程底座收紧；
2. 选一个核心业务纵切面做真闭环；
3. 将演示模块、真实模块、待接入模块分层管理。

## 2. 当前项目定位

### 2.1 它现在是什么

从代码和文档综合判断，这个项目当前更接近：

- 一个 **面向基层治理/网格化场景的业务产品原型**
- 一个 **Web 管理端 + 移动端小程序工作台** 的联合演示系统
- 一个 **设计系统已建立、业务内核尚未产品化** 的中后期前端原型仓库

### 2.2 它现在不是什么

它暂时还不是：

- 一个具备后端、鉴权、真实 API、持久化策略的完整业务系统
- 一个有类型安全、自动化测试、静态检查和清晰边界的工程化前端项目
- 一个真实接入 LLM、知识库、规则引擎的智能体产品

## 3. 项目结构拆解

### 3.1 技术栈与运行方式

从 `package.json` 看，项目基于 `Vite + React`，使用 `Tailwind CSS v4`、`Radix UI/shadcn`、`Recharts`、`sonner`、`lucide-react` 等组件体系，脚本只有 `dev` 和 `build` 两个入口，没有 lint、test、typecheck 脚本，也没有显式 `typescript` 依赖。【证据：`package.json` 只有 `dev/build` 脚本，且 devDependencies 里没有 `typescript`】

### 3.2 应用入口与壳层

应用壳层非常薄：

- `src/main.tsx` 只负责挂载 `App`
- `src/app/App.tsx` 负责页面壳层布局、侧栏/顶部栏与“当前路由”状态
- `src/app/components/Routes.tsx` 用 `switch` 做页面切换

这说明当前项目是 **单页状态式壳层**，不是 URL 驱动的路由应用。

### 3.3 页面规模

当前代码规模已经不小：

- `pages` 目录 30 个页面文件
- `mobile` 目录 32 个页面文件
- `ui` 目录 46 个基础组件文件
- `seeds` 目录 8 个数据种子文件
- `src` 总计约 5.5 万行

其中多个页面文件已经非常大：

- `TagOverview.tsx` 约 2400 行
- `PopulationManagement.tsx` 约 2300 行
- `HousingManagement.tsx` 约 1700 行
- `RelationshipManagement.tsx` 约 870 行
- `MobilePersonDetail.tsx` 约 840 行

这类体量已经不是“复杂页面”问题，而是 **模块边界失控** 的信号。

### 3.4 数据层

当前真实运行数据来源主要是 `src/app/services/db.ts`：

- 首次运行将 `SEED_PEOPLE / SEED_HOUSES / SEED_GRIDS / SEED_VISITS / SEED_CONFLICTS` 等写入 `localStorage`
- 所有页面通过 `db.getPeople()`、`db.getHouses()`、`db.updatePerson()` 等方法读写
- 更新后通过自定义事件 `db-change` 通知 UI 刷新

这套设计非常适合原型和演示，但本质仍是：

- 前端本地伪数据库
- 单窗口事件总线
- 无 schema 迁移
- 无并发控制
- 无服务端规则校验
- 无会话级身份隔离

### 3.5 设计系统

设计系统是这个项目最成熟的一层：

- `src/styles/theme.css` 已经沉淀出品牌色、状态色、中性色、圆角、阴影、字体、间距、图表色
- `src/app/config/ui-constants.ts` 和 `chartConfig.ts` 进一步把页面间距、动画、断点、图表配色做了常量化

这意味着视觉规范已经从“页面手写样式”提升到了“可复用 token 层”，是这个仓库最有价值的长期资产之一。

### 3.6 Web 与移动端关系

当前是两个并存的前端壳：

- Web 管理端：侧栏 + 顶栏 + 页面内容
- 移动端：`MobileApp` 内部维护一个自定义 history 栈

它们共享部分领域数据，但没有共享统一导航模型，也没有共享统一状态容器或统一的领域服务层。

这会导致：

- Web 与移动端功能演进容易分叉
- 相同数据对象在两个端的处理逻辑重复
- 后续一旦接后端，接入成本会成倍上涨

## 4. 关键发现

## 4.1 设计系统已经可用，是项目最稳的部分

`theme.css` 已经建立完整的视觉 token 层，包括品牌主色、功能色、中性层级、圆角、阴影、字号、字重、间距和深色模式图表配色。这部分明显不是临时拼装，而是经过多轮整理后的稳定基线。

结论：

- 视觉层继续优化不应再以“页面逐个修颜色”为主
- 应该把后续迭代重心从“继续补 UI”转到“让业务与工程结构跟上这套 UI”

## 4.2 路由体系是当前最明显的工程短板之一

`App.tsx` 用本地状态 `currentRoute` 保存当前页面，而不是使用浏览器路由；`Routes.tsx` 则用 `switch` 映射页面。`StatisticsOverview.tsx` 内部却又直接通过 `window.location.href = '/demographics-analysis'` 这类方式跳转页面。

这会产生一个明确问题：

- 页面内部点击“深度分析入口”时，跳转的是 URL
- 但应用真正的导航状态保存在 React state，不读取 URL
- 结果是深链、刷新和内部跳转的行为不一致，部分入口逻辑上就是失效的

这个问题不是体验瑕疵，而是 **继续加页面之前必须先修的壳层问题**。

## 4.3 数据层已经有统一入口，但仍是“原型级统一”

`db.ts` 的统一入口做得比很多原型项目好，至少避免了页面各自维护随机数据源。但它仍然只解决了“本地演示共享数据”的问题，没有解决：

- 领域规则集中化
- 查询/写入约束
- 服务端同步模型
- 草稿/正式数据差异
- 审计日志和权限边界

所以现在的数据层更像：

**统一的 mock 仓库，而不是可演进的业务仓库。**

## 4.4 多个页面仍然深度依赖 mock 数据，且与统一数据层并存

这是当前最影响后续迭代效率的问题之一：

- `TagOverview.tsx` 自己维护 `mockTags`，同时又读取 `db` 中的人口数据做覆盖分析
- `RelationshipManagement.tsx` 完全建立在本地 `mockRelationships`、`mockPersons`、`mockHouses` 上
- `QuickNote.tsx` 先用页面内 `mockPeople` 做联想，再把结果写回 `db`
- `SmartAgentPages.tsx` 直接用 `setTimeout` 返回“模拟回复”

这说明目前仓库里并存着三类功能：

1. 真正读统一种子数据的页面
2. 半真半假的混合页面
3. 纯演示页面

如果不先给这些页面分级，后续每次“接真实能力”都会先花时间辨认哪些代码能复用、哪些必须推倒。

## 4.5 单页文件过大，业务规则散落在组件内部

`PopulationManagement.tsx`、`HousingManagement.tsx`、`TagOverview.tsx` 这类文件同时承担了：

- 页面布局
- 过滤条件
- 规则判断
- 数据映射
- 弹窗状态
- 表单逻辑
- 可视化片段

这会带来三个后果：

- 局部修改必须读完整页，改动成本高
- 很难为“业务规则”单独测试
- AI 或新工程师接手时，理解门槛极高

用 Ousterhout 的术语，这里大量存在的是 **浅模块**，不是深模块。

## 4.6 类型安全几乎没有真正建立起来

项目文件是 `.ts/.tsx`，但工程约束并没有跟上：

- 没有 `tsconfig`
- 没有 `typescript` 依赖
- 没有 `npm run typecheck`
- 没有 lint
- 没有测试

一个很直观的例子是：`DemographicsAnalysis.tsx` 和 `AnomalyAnalysis.tsx` 从 `../../services/db` 导入了 `Person`，但 `db.ts` 并没有导出这个类型。之所以构建仍能通过，本质上是因为现在的构建链并没有把这类类型层问题作为失败条件。

这意味着目前的“可构建”并不等于“类型可靠”。

## 4.7 移动端存在明显的演示式状态管理痕迹

`MobileProfile.tsx` 切换网格后直接 `window.location.reload()`；`MobileApp.tsx` 则自己维护内存历史栈；移动端多个模块依赖 `localStorage` 中的 `current_grid`、`mobile_user` 等键值。

这对于演示是高效的，但对于继续演进是不稳定的，因为：

- 刷新会丢失部分运行上下文
- 页面之间依赖隐式 key，而不是显式状态流
- 一旦要接鉴权、接口、权限、草稿态，就会大面积返工

## 4.8 存在一批大体量但未接入运行时的 Figma 导出文件

`src/imports` 目录大约 1.4M，包含 30+ 个设计导出文件，但当前代码中没有发现它们被实际引用。

这类文件的风险不在“占空间”，而在于它们会：

- 干扰代码搜索
- 增加 AI/工程师理解噪音
- 让仓库边界变得不清楚

建议把它们明确标为 `design-source` 或迁出运行目录。

## 4.9 文档体系丰富，但已经开始出现“进度叙事”和“真实工程状态”脱节

仓库里有大量阶段性总结、设计规范、检查清单和暗色适配文档。这本来是好事，但目前它们已经开始出现两个问题：

- 多份文档对“完成度”的表述并不一致
- 文档更偏向记录视觉重构进展，而不是业务能力成熟度

后续如果继续依赖这些文档指导迭代，建议改成两套看板：

1. 视觉/设计系统进度
2. 业务/工程化进度

否则“95% 完成”这类表述很容易误导下一轮决策。

### 5.2 工程成熟度评分

我给当前项目的分项判断如下：

| 维度 | 评分 | 判断 |
|------|------|------|
| 视觉设计系统 | 8.5/10 | 已成体系，可复用 |
| 页面覆盖度 | 8/10 | 足够支撑方案展示与流程讨论 |

| 数据架构 | 4.5/10 | 有统一入口，但仍是原型级 |

## 6. 最值得优先处理的 7 个问题

### P0. 统一导航模型

先把 Web 和移动端至少各自变成“可预测导航”：

- Web 端接 `react-router`
- 移动端也统一到可序列化路由状态
- 禁止页面内部再直接写 `window.location.href`

### P0. 建立工程基线

至少补齐：

- `typescript`
- `tsconfig.json`
- `npm run typecheck`
- `eslint`
- 最少一层单元/集成测试基线

没有这层，后面的任何重构都只是“更大的手工改动”。

### P0. 给页面分级：真实 / 半真实 / 演示

建议立刻建立页面分级清单：

- A 类：基于 `db.ts` 主数据，可继续产品化
- B 类：混合 mock，需要重构后才能继续
- C 类：纯演示，只保留展示职责

这一步会极大降低后续“误判现状”的成本。

### P1. 选择一个核心纵切面做真闭环

我建议优先做：

**人口 -> 房屋 -> 走访 -> 标签/风险**

原因：

- 数据对象已存在
- Web 和移动端都已覆盖
- 能形成最小治理业务闭环
- 后续接 AI、规则、报表都能挂在这条链路上

### P1. 拆大页面，沉淀领域层

优先拆：

- `PopulationManagement`
- `HousingManagement`
- `TagOverview`
- `RelationshipManagement`

拆分目标不是“拆文件”，而是沉淀出：

- `domain/services`
- `selectors`
- `form schemas`
- `mapping/adapters`
- `query hooks`

### P1. 建立统一数据访问边界

把目前 `db.ts` 直接暴露给页面的方式，逐步替换成领域仓库或服务：

- `personRepository`
- `houseRepository`
- `visitRepository`
- `tagService`
- `conflictService`

这样后续把 `localStorage` 换成 API 时，才不会全仓硬替换。

### P2. 清理设计源文件与文档噪音

把 `src/imports` 和“仅供参考”的文档明确归档，不要继续混在运行目录和主认知路径里。

## 7. 推荐的下一阶段迭代路线

## 阶段 A：一周内完成的“底座校准”

目标：让项目从“能演示”变成“能安全继续改”

建议任务：

1. 补 `typescript`、`tsconfig`、`typecheck`
2. 接入 `react-router`
3. 建立 `src/app/domain` 或 `src/app/features` 目录边界
4. 给页面做 A/B/C 分级
5. 移除或隔离未引用的 `src/imports`

输出结果：

- 工程约束基线
- 可追踪的页面分级清单
- 明确的下一轮重构边界

## 阶段 B：两周内完成的“核心闭环产品化”

建议只聚焦一个纵切面：

- 人口管理
- 房屋管理
- 移动端人员/房屋详情
- 走访记录
- 标签与风险联动

输出结果：

- 一条真实可演示的业务闭环
- Web/移动端共享的核心领域模型
- 后续可扩展到报表、预警、规则、AI 的基础

## 阶段 C：再进入 AI / 规则 / 报表强化

在核心闭环稳定之前，不建议优先做：

- 真正的 LLM 接入
- 复杂自动规则
- 大量新增分析页面
- 更深的视觉 polish

否则会继续放大“前端演示很多，但核心能力不落地”的问题。

## 8. 我对后续迭代的明确建议

### 建议 1

不要再把“页面数量”当作进度主指标，改用“真实闭环数量”。

### 建议 2

不要继续平均打磨所有模块，先冻结演示模块，把资源集中到一个最有价值的业务主链。

### 建议 3

把“设计系统工程”与“业务工程”拆开管理。前者基本完成，后者才刚开始进入真正的收敛期。

### 建议 4

下一轮如果让我继续推进，最合理的工作方式不是直接再加页面，而是先做一份：

- 页面分级清单
- 核心领域模型图
- 第一批重构任务拆解

然后再进入代码实施。

---

## 9. 结论

这个项目值得继续做，原因不是它“已经差不多完成”，而是它已经跨过了最难的“从空白到可讨论原型”阶段。

但它接下来最需要的，不是继续横向铺开，而是纵向收口：

- 从展示型仓库，收口成可演进仓库
- 从页面堆叠，收口成领域边界
- 从 mock 驱动，收口成真实业务闭环

一句话总结：

**现在最应该做的不是“再多做几个模块”，而是把这个项目从高保真原型，推进成一个有工程抓手的 MVP 基座。**
